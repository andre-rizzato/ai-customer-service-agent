1. Visão geral e origem

Este projeto implementa, em código, o runbook "Agente de atendimento por IA no WhatsApp, do zero à produção" — mas de forma agnóstica de canal. A ideia central do runbook original é replicável para qualquer plataforma de mensagens: uma base de conhecimento fechada (o agente nunca inventa specs, preços ou prazos), transparência total quando perguntado se é uma IA, e um handoff limpo para um atendente humano quando a conversa sai do escopo.

Em vez de acoplar essa lógica ao WhatsApp, o projeto isola tudo que é específico de plataforma atrás de uma interface (ChannelAdapter), e tudo que é regra de negócio (RAG, prompt, handoff, log) em um Orchestrator único e compartilhado. O resultado: o mesmo comportamento de atendimento funciona hoje no Telegram e no WhatsApp, e amanhã em qualquer outro canal que implemente a mesma interface.

Por que isso importa Se o objetivo é oferecer isso como serviço para múltiplos clientes/negócios, cada um pode rodar sua própria instância com seu próprio catálogo, tom de voz e canal preferido — sem duplicar nem uma linha da lógica de atendimento.

2. Arquitetura

Cinco peças, cada uma isolada atrás de uma interface própria — trocar a implementação de qualquer uma não exige mudanças nas outras:

1 · Canal (ChannelAdapter)
Recebe o webhook da plataforma, normaliza para InboundMessage, envia a resposta de volta. Implementações: Telegram, WhatsApp Cloud API, Web (REST simples para testes).
2 · Orquestrador
Pipeline central: rate limit → gatilho de handoff → RAG → prompt → LLM → log. Não sabe de onde a mensagem veio nem para onde a resposta vai.
3 · LLM (LLMProvider)
Gera a resposta em linguagem natural a partir do contexto recuperado — nunca da memória própria do modelo. Implementações: Anthropic (Claude), OpenAI.
4 · Base de conhecimento (RAG)
Catálogo, specs, políticas, preços — indexados como embeddings em um vector store local. Implementações de embedding: Voyage AI (padrão), OpenAI, local (offline).
5 · Handoff (HandoffNotifier)
Regra de transferência + histórico anexado. Implementações: console (dev), webhook (Slack/Discord/custom).

3. Fluxo de uma mensagem

Implementado em src/orchestrator/orchestrator.ts, método handleMessage() — o mesmo caminho para qualquer canal:

Mensagem chega (Telegram / WhatsApp / Web) │ ▼ ChannelAdapter normaliza → InboundMessage │ ▼ 1. Rate limiter (por conversa) │ ▼ 2. Gatilho de handoff? (palavra-chave / frustração) ├─ Sim → HandoffNotifier avisa humano c/ histórico │ responde "vou te conectar" → FIM └─ Não → continua │ ▼ 3. Busca RAG (embeddings + cosine similarity, top-K, corte de relevância) │ ▼ 4. Monta system prompt (3 regras fixas + contexto + tom de voz) │ ▼ 5. Chama o LLM (Claude ou OpenAI) │ ▼ 6. Grava turno no histórico + log de auditoria (JSONL) │ ▼ ChannelAdapter envia a resposta de volta

6. Configuração: negócio vs. ambiente

O projeto separa deliberadamente dois tipos de configuração, cada um com seu próprio arquivo e propósito:

config/agent.config.json.env
NaturezaConfiguração do negócioSegredos e ambiente de execução
ExemplosNome do negócio, tom de voz, palavras de handoff, top-K do RAGChaves de API, tokens de canal, portas, caminhos de dados
VersionamentoPode ser versionado por cliente/negócioNunca commitado (.gitignore)
Quem defineO negócio, na Fase 0 (briefing)Quem opera a infraestrutura

Os dois são carregados e validados (com zod) uma única vez, em src/config.ts, na inicialização do processo — qualquer campo ausente ou mal formatado falha imediatamente, com mensagem clara, em vez de quebrar silenciosamente no meio de uma conversa.

7. Base de conhecimento e RAG

Cada linha do catálogo (knowledge/catalog.example.json) representa um produto, serviço ou política, no formato:

{ "id": "filtro-fx200", "title": "Filtro FX200", "content": "specs, preço, garantia, FAQ..." }

O script npm run ingest lê esse catálogo, gera um embedding por item (via Voyage/OpenAI/local) e grava tudo numa coleção do Qdrant (local em dev, Azure Container Apps em produção). Em tempo de resposta, a busca combina similaridade semântica (Qdrant) com palavra-chave (BM25), funde os dois rankings (RRF) e reordena os candidatos com o rerank da Voyage. Os topK trechos acima de minRelevanceScore entram no prompt.

A busca roda primeiro com a pergunta do cliente. Só quando o melhor trecho fica abaixo de hydeSkipScore ela tenta de novo com HyDE: uma passagem hipotética, gerada pelo LLM no estilo do catálogo, ajuda em perguntas indiretas. Detalhes em docs/RAG_QDRANT_MIGRATION.md; custo e números medidos em docs/CUSTO_API.md.

Memória da conversa: o LLM recebe só os últimos historyWindowTurns turnos (padrão 15). O que sai da janela volta como um resumo acumulado e como trechos antigos relevantes (src/conversation/memory.ts). Assim o custo de uma conversa longa não cresce sem limite, e o bot continua lembrando do que foi dito no começo.

Regra de vazio Se nenhum item passar no corte de relevância, o prompt informa explicitamente "nenhum trecho relevante encontrado" — é isso que permite à regra fixa nº 1 instruir o modelo a admitir que não sabe, em vez de inventar uma resposta.

8. Handoff para humano

Roda antes da busca RAG e da chamada ao LLM (mais barato e mais previsível que deixar o próprio modelo decidir). Dois gatilhos, configuráveis em agent.config.json:

  • Pedido explícito — lista handoffKeywords (ex.: "falar com atendente").
  • Frustração — lista frustrationKeywords (ex.: "péssimo", "não aguento").

Quando dispara, o HandoffNotifier configurado recebe o histórico completo da conversa (não só a última mensagem) e o usuário recebe uma resposta padrão avisando que será conectado a um atendente. A regra 3 do prompt (ver Seção 9 do guia de deploy) reforça o mesmo comportamento como segunda camada, para casos que a lista de palavras-chave não cobrir.

Adicionar um novo canal (Instagram, SMS, etc.) significa implementar a interface ChannelAdapter e registrá-lo em src/server.ts — nenhuma linha do Orchestrator muda.

10. Testes

A suíte automatizada (npm test, Vitest) cobre a parte determinística da matriz de testes da Fase 5 do runbook original — detecção de handoff, montagem do prompt, rate limiting, ranking da busca (BM25/RRF), relay de handoff, memória da conversa e medição de custo — sem depender de nenhuma API externa. A qualidade com LLM de verdade é medida sob demanda pelo eval RAGAS e pelo teste de conversa longa (eval/README.md). O script npm run simulate complementa isso com um chat interativo no terminal, para rodar manualmente os casos que dependem do LLM responder (pergunta dentro/fora do escopo, "você é IA?", reclamação).
