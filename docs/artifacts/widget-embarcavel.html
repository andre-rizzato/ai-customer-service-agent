A pergunta que originou este documento: se o DistributedOrderSystem (Python + .NET) e o agente de atendimento (Node, este repo) são "dois mundos" crescendo em paralelo, qual a estratégia pra adicionar um widget de chat embarcável — algo que um cliente plante no próprio site, contornando a burocracia de aprovação do WhatsApp/Telegram — sem duplicar trabalho entre os dois?

Investigação direta nos dois repositórios (não só documentação) mostrou que o problema real não é "duas linguagens crescendo" — é três portas de entrada conversacionais já existentes, apontando pra cérebros de qualidade desigual. O widget que o DistributedOrderSystem já tem (ChatbotService/wwwroot/chat-widget, JS puro, sem build, com modo "Direct" documentado explicitamente para "External Projects/Corporate Website") já serve o caso de uso — só aponta pro cérebro errado: o AgentService (Python/LangGraph) é um microsserviço estreito de status/cancelamento de pedido, prompt fixo em inglês, sem RAG nem tom configurável — nunca foi desenhado pra ser um agente de atendimento geral.

Decisões

Um cérebro, duas mãos

Decisão · cérebro único

O Node Orchestrator continua sendo a única porta conversacional — WhatsApp, Telegram e agora o widget embarcável, todos normalizados pro mesmo pipeline (ChannelAdapter já existe pra isso). O AgentService não vira um "cérebro geral": continua estreito, chamado pelo Node só quando capabilityRouter detecta intenção de pedido — exatamente o papel que já exerce hoje, sem nenhuma mudança necessária nele.

Decisão · não fundir runtimes

Reescrever um dos dois lados (TypeScript ↔ Python/.NET) pra eliminar "dois mundos" seria trabalho grande, caro e arriscado, sem ganho real — a fronteira de responsabilidade já é limpa (Node = conversa/canal; AgentService/.NET = execução de domínio). Mesmo critério de custo/benefício já registrado no CLAUDE.md deste repo pra decisões de infraestrutura se aplica aqui a decisões de runtime.

Decisão · multi-tenant

Vender o widget como serviço não exige lógica nova de "qual tenant é esse" dentro de um processo compartilhado — o desenho multi-tenant já registrado (par agente-node + agent-service por cliente, Managed Identity e Key Vault próprios) já cobre exatamente este caso. Só precisa ser provisionado quando aparecer o primeiro cliente pagante do gadget — mesma condição de gatilho já registrada em docs/STATUS.md.

Execução

Plano faseado

  • Fase 1 — remover o HTML legado hardcoded em ChatController.cs (DistributedOrderSystem) e a referência morta na documentação. Build do ChatbotService validado (0 erros, 0 avisos).
  • Fase 2 — endurecer o canal web do Node pra uso público: CORS por allowlist de origem (WIDGET_ALLOWED_ORIGINS), aplicado só em /webhook/web. Testado: preflight OPTIONS, origem autorizada (headers corretos), origem não autorizada (sem headers — browser bloqueia sozinho), e same-origin local (sem regressão no whatsapp.html).
  • Fase 3 — repontar o chatbotServiceUrl do widget JS (hoje /api/chat, via ChatbotService) pro endpoint público novo do Node; confirmar que nada no widget assume a marca "DistributedOrderSystem" de forma fixa.
  • Fase 4 — nenhuma mudança esperada no AgentService: validar que o fluxo de intenção de pedido continua idêntico depois da Fase 3 (chamado pelo Node, não mais pelo widget direto).
  • Fase 5 — quando aparecer o 1º cliente pagante do gadget: provisionar o par container + User-Assigned Managed Identity + Key Vault já desenhado, aproveitando a janela da migração do DistributedOrderSystem pro Azure em vez de fazer essa migração duas vezes.
