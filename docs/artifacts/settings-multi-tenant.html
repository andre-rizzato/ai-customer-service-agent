Pedido: alguém loga no site (www.rizzatotech.com) e vê a tela de configuração do próprio bot — pensando em vários clientes futuros, não só a Rizzato Tech. Hoje isso não existe em nenhum grau: o site não tem banco de dados, não sabe o que é um "bot", e só existe um bot de verdade no ar. A tela de configuração atual (rizzato-tech.rizzatotech.com/settings.html) já tem login (Firebase, concluído em 11-12/10/2026), mas decide quem é admin por uma lista fixa (ADMIN_EMAILS) escrita no .env daquela VM — um bot, uma lista, sem noção de "de quem é esse bot".

Este documento não implementa nada — é o mapa das peças que faltam e de onde está o risco, pra decidir COMO atacar isso antes de escrever a primeira linha.

Onde está o risco de verdade

O modelo de confiança muda, não só a tela

Risco principal

Hoje, cada bot é seu próprio mundo isolado: um processo, um .env, uma lista fixa ADMIN_EMAILS. Um vazamento ou bug num bot não dá acesso a nenhum outro — não existe "outro" pra vazar. O passo 6 muda isso: a decisão de quem pode administrar qual bot passa a vir de um lugar central (Firestore) que todos os bots consultam. Se as regras de segurança desse Firestore forem fracas, ou se o cliente (navegador) puder escrever nessa coleção, um usuário poderia se adicionar como admin de um tenant que não é dele.

  • Regra inegociável: a coleção tenants só pode ser escrita por código de servidor (Admin SDK, com uma Service Account), nunca pelo SDK do cliente no navegador — igual ao princípio que já guia ADMIN_EMAILS hoje ("a lista só muda editando o .env e reiniciando, nunca pela própria tela").
  • Cada bot continua validando a assinatura do token Firebase sozinho (não muda — verifyFirebaseIdToken já faz isso sem depender de rede nenhuma além das chaves públicas do Google). Só a pergunta "este uid é admin?" passa a ter uma segunda fonte possível, além do .env.
  • Pergunta a decidir antes de implementar: o bot consulta o Firestore diretamente a cada requisição (mais uma dependência de rede por chamada, ver eixo "overhead" do CLAUDE.md), ou o Firestore grava um custom claim no próprio token do usuário (sem round-trip extra, mas exige um Cloud Function pra manter o claim atualizado quando o vínculo mudar)?

Sequência sugerida

Fases — cada uma entrega algo testável sozinha

  • 1
    Firestore com o modelo de dados, editado à mão Cria a coleção tenants (um documento por cliente: adminUids[], apiBaseUrl, nome). Sem UI de provisionamento ainda — você mesmo cria o documento pelo Firebase Console. Testável isoladamente: uma função que recebe um uid e devolve o tenant certo.
  • 2
    requireAdmin v2 num bot só Troca ADMIN_EMAILS por uma consulta ao Firestore (ou claim customizado — decisão da seção de risco acima) no bot da própria Rizzato Tech primeiro. Testável sem tocar no site: continua acessando rizzato-tech.rizzatotech.com/settings.html direto.
  • 3
    Página "minha conta" no site Nova rota no Next.js: loga, consulta o tenant, redireciona (ou chama a API direto, com CORS configurado no bot) pra tela de configuração certa. Testável de ponta a ponta com o tenant único da fase 1.
  • 4
    Provisionamento (quando houver um segundo cliente de verdade) Processo (manual ou com script) pra criar: o documento no Firestore, o processo PM2/container do bot, a config própria daquele cliente — ligado ao desenho "Implantação multi-tenant" já existente. Não vale a pena automatizar antes de ter o segundo cliente real.

Fora de escopo por agora

O que este plano deliberadamente não resolve

Adiado
  • UI de autoatendimento pra um cliente se cadastrar e já sair com um bot rodando — hoje continua sendo um processo manual seu (criar a VM/container, a config, o documento no Firestore).
  • Cobrança/plano — este documento é só sobre "quem vê o quê", não sobre billing.
  • Login por e-mail/senha como caminho de admin confiável — continuaria exigindo verificação de e-mail (sendEmailVerification), que não está implementada; não é bloqueador deste desenho, mas é outra peça faltando se alguém insistir em não usar Google/Microsoft/Facebook.
