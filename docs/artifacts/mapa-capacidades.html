Até aqui o agente resolvia um caso: pedido, contra o GatewayBff do DistributedOrderSystem. Pra vender o serviço pra qualquer negócio que precise de vendas ou atendimento — barbearia, salão, clínica, loja — o acoplamento com um backend específico precisa sair do meio do caminho. A ideia: três capacidades de domínio, cada uma com um conector plugável atrás — o mesmo padrão que já existe duas vezes nesse ecossistema (ChannelAdapter no agente Node, LLMProvider/EmbeddingProvider também) — só que agora resolvendo "qual sistema real o negócio do cliente usa", não "qual provedor de IA".

Papel do DistributedOrderSystem aqui: é o protótipo do mundo real que demonstra o serviço funcionando contra um backend de verdade — não é dependência fixa. O AgentService é implantado como serviço standalone e invocado por quem precisar (o agente Node deste projeto, o próprio DistributedOrderSystem, ou outro sistema no futuro) — o contrato HTTP já nasceu genérico por isso.

Segurança do checkout

O agente nunca vê dado de cartão

Princípio

O agente negocia, mostra produto, aplica desconto dentro das regras configuradas — mas o pagamento em si sempre acontece numa página hospedada pelo processador (Stripe Checkout, Mercado Pago, PagSeguro), nunca dentro da conversa do WhatsApp/Telegram. O que o agente faz é gerar e enviar o link; o "ambiente protegido" pedido é literalmente essa página do processador, não uma tela construída por nós.

  • Nenhum número de cartão, CVV ou dado sensível trafega pelo LLM ou pelos logs de conversa.
  • O escopo de compliance (PCI-DSS) fica inteiro com o processador de pagamento, não com o agente.
  • Mesmo modelo de segredo já usado no resto do projeto: credencial do processador fica no Key Vault, nunca em texto plano.

Fora da arquitetura de dados

Duas coisas que não são um componente novo

Negociar e argumentar não é uma peça de arquitetura — é comportamento do próprio LLM, configurado em agent.config.json (tom, regras de desconto permitidas) e alimentado pelos dados reais que o SalesBackend devolve (preço, estoque, promoção ativa). Sem esse dado real, o agente só poderia blefar — por isso a capacidade vem antes da personalidade.

Mostrar o produto via WhatsApp é capacidade do canal, não do backend — a Meta Cloud API tem suporte nativo a mensagens de catálogo/produto e botões interativos, bem além do texto simples que o ChannelAdapter usa hoje. É extensão do canal, trabalho separado dos connectors.

Decisões

As três perguntas em aberto, resolvidas

Decisão · pagamento

Cartão de crédito, débito e Pix saem de um único processador: PagSeguro (PagBank) pra clientes brasileiros — não de três integrações separadas pra cobrir os três métodos. O checkout hospedado do PagSeguro já oferece os três numa tela só, e é o mais usado por pequenos negócios no Brasil. Primeiro conector a construir: PagSeguroCheckoutBackend.

Stripe entra como segundo conector, não como alternativa descartada — pra quando o cliente final do negócio estiver fora do Brasil (ou o próprio negócio vender em dólar/outra moeda). PagSeguro e Pix são irrelevantes fora do Brasil; Stripe é o padrão de fato pra cartão internacional, multi-moeda e cobrança recorrente. Os dois convivem como PaymentLinkBackend intercambiáveis — a escolha vira config por cliente (mercado doméstico → PagSeguro, mercado internacional → Stripe), do mesmo jeito que LLM_PROVIDER já escolhe entre Anthropic e OpenAI hoje.

  • Mercado Pago fica como terceiro conector natural — mesmo molde, pra cliente que já usa ele ou atende América Latina de forma mais ampla.
Decisão · implantação

Nem processo único compartilhado (zero isolamento — um bug vaza dado entre clientes) nem 1 VM por cliente pra sempre (não escala — N clientes = N VMs pra patchear e pagar 24h/dia, mesmo ociosas). O meio-termo: VM compartilhada, 1 container Docker por cliente (o Dockerfile já existe no repo), cada container com sua própria identidade e seu próprio Key Vault. Detalhe de arquitetura completo na próxima seção.

Decisão · roteamento

Confirmado: cada cliente liga/desliga capacidades (RAG, Scheduling, Sales, Order, handoff humano) numa tela de configuração — o orchestrator só considera rotear pra uma capacidade se ela estiver habilitada pro cliente daquela conversa. A mesma lista de capacidades habilitadas vira, naturalmente, a unidade de precificação: mais componente ligado, plano mais caro.

Detalhe · implantação multi-tenant

Um VM, N clientes, isolamento real

A peça que faltava: numa VM compartilhada, a Managed Identity de sistema (a que a VM já usa hoje) é uma só pra VM inteira — não dá pra usar ela pra separar cliente A de cliente B. A saída é o Azure permitir várias User-Assigned Managed Identities na mesma VM: uma por cliente, cada uma com permissão só no Key Vault daquele cliente. O container de cada cliente informa qual identidade usar (AZURE_CLIENT_ID) — continua sem credencial nenhuma em disco, só que agora isolado por cliente mesmo compartilhando host.
