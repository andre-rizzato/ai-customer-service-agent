Persistência dos dados CONVERSATIONS_DIR (histórico e resumos .memory.json), AUDIT_LOG_PATH e USAGE_LOG_PATH vivem em disco local. Em qualquer deploy containerizado ou com múltiplas réplicas, isso PRECISA ser um volume persistente — sem isso, um redeploy apaga o histórico, a memória das conversas e a base do relatório de custo. O índice do catálogo fica no Qdrant, fora do processo.

3. Setup local passo a passo

1
Clonar o repositório e instalar dependências: npm install
2
Copiar os templates: cp .env.example .env e cp config/agent.config.example.json config/agent.config.json
3
Preencher .env com as chaves de LLM/embeddings (Seção 2) e config/agent.config.json com nome do negócio, tom de voz e gatilhos de handoff (Fase 0: defina isso com o negócio antes de codar)
4
Editar/substituir knowledge/catalog.example.json pelo catálogo real (uma linha por produto/serviço/política)
5
Indexar a base: npm run ingest — repita sempre que o catálogo mudar
6
Testar sem canal nenhum: npm run simulate — rode a matriz de testes da Fase 5 (dentro do escopo, fora do escopo, "você é IA?", pedido de humano, reclamação, mensagem ambígua)
7
Rodar a suíte automatizada: npm test
8
Só depois de validar os passos 6 e 7, seguir para a Seção 4 ou 5 (deploy)

4. Deploy com Docker

O Dockerfile na raiz do projeto faz build multi-stage: compila TypeScript em um estágio com as devDependencies, e a imagem final roda só o JavaScript compilado com node puro (sem tsx, sem TypeScript instalado) — imagem menor e sem ferramentas de build na superfície de produção.

# build da imagem
docker build -t ai-customer-service-agent .

# rodar com variáveis de ambiente e volume de dados persistente
docker run -d \
  --name agente-atendimento \
  -p 3000:3000 \
  --env-file .env \
  -v $(pwd)/data:/app/data \
  ai-customer-service-agent
Catálogo e configuração customizados na imagem O Dockerfile copia config/agent.config.example.json e knowledge/catalog.example.json como fallback funcional. Para produção, monte seus arquivos reais por volume (-v $(pwd)/config/agent.config.json:/app/config/agent.config.json e o equivalente para o catálogo) ou construa uma imagem própria por cliente copiando os arquivos reais no lugar dos exemplos.

Depois de subir o container, rode o ingest uma vez (dentro do container ou apontando VECTOR_STORE/dados para o mesmo volume montado):

docker exec -it agente-atendimento node dist/src/knowledge/ingest.js

docker-compose (opcional)

services:
  agente:
    build: .
    ports: ["3000:3000"]
    env_file: .env
    volumes:
      - ./data:/app/data
      - ./config/agent.config.json:/app/config/agent.config.json
      - ./knowledge/catalog.json:/app/knowledge/catalog.json
    restart: unless-stopped

5. Deploy sem Docker (processo direto / PM2)

Alternativa em uma VPS comum, sem containers:

1
Na VPS: git clone, npm ci, configurar .env e config/agent.config.json
2
Compilar: npm run build
3
Rodar o processo com um gerenciador que reinicia sozinho em caso de crash — pm2 start dist/src/server.js --name agente-atendimento (ou um serviço systemd equivalente)
4
Colocar um proxy reverso (Nginx/Caddy) na frente, com TLS, apontando para a porta do processo (PORT no .env)
5
Rodar npm run ingest uma vez após o deploy (e a cada atualização do catálogo)

6. Configurar o canal Telegram

1
Criar um bot com o @BotFather no Telegram e copiar o token gerado
2
Definir TELEGRAM_BOT_TOKEN (e um TELEGRAM_WEBHOOK_SECRET à sua escolha) no .env
3
Com o servidor já publicado em uma URL HTTPS pública, registrar o webhook:
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=<SUA-URL-PUBLICA>/webhook/telegram&secret_token=<TELEGRAM_WEBHOOK_SECRET>"
4
Confirmar: mande uma mensagem para o bot no Telegram e verifique se a resposta chega
Testando localmente antes de ter domínio público Use um túnel (ex.: ngrok http 3000) para gerar uma URL HTTPS temporária apontando para sua máquina local, e use essa URL no setWebhook acima.

7. Configurar o canal WhatsApp (Meta Cloud API)

1
Criar um app no Meta for Developers e adicionar o produto WhatsApp
2
Copiar WHATSAPP_ACCESS_TOKEN e WHATSAPP_PHONE_NUMBER_ID do painel do app
3
Definir WHATSAPP_VERIFY_TOKEN — uma string à sua escolha, usada só no handshake de verificação
4
No painel do Meta, configurar o webhook apontando para <SUA-URL-PUBLICA>/webhook/whatsapp, usando o mesmo WHATSAPP_VERIFY_TOKEN — a Meta faz uma chamada GET de verificação automaticamente
5
Assinar o webhook para o campo messages
6
Confirmar: mande uma mensagem de teste para o número WhatsApp Business e verifique a resposta
Número verificado para clientes reais Para atendimento comercial de verdade, use um número WhatsApp Business verificado, conectado ao webhook de PRODUÇÃO — separado do número/ambiente usado nos testes acima (Fase 6 do runbook original).

8. Checklist completo de lançamento

Antes de codar (Fase 0)

  • Escopo fechado: 10–20 perguntas frequentes reais do negócio listadas
  • Histórico de 15–20 conversas reais revisado (tom de voz, jeito de falar)
  • Critério de sucesso mensurável definido (taxa de resolução, tempo de resposta)

Configuração

  • .env preenchido com chaves de LLM e embeddings válidas
  • config/agent.config.json preenchido (nome do negócio, tom, gatilhos de handoff, rate limit)
  • knowledge/catalog.json com o catálogo real do negócio (não o example)
  • npm run ingest executado com sucesso após o catálogo real

Testes (Fase 5 — não pular)

  • npm test passando (handoff, prompt, rate limit, vector store)
  • npm run simulate: pergunta dentro do escopo respondida corretamente com base no catálogo
  • npm run simulate: pergunta fora do escopo → bot admite que não sabe, nunca inventa
  • npm run simulate: "você é uma IA?" → resposta de transparência total
  • npm run simulate: pedido explícito de atendente → handoff dispara
  • npm run simulate: mensagem de reclamação/frustração → handoff dispara
  • Matriz de testes rodada por 2+ pessoas diferentes (evita viés de quem escreveu o prompt)

Infraestrutura

  • Volume/persistência configurado para data/ (histórico + auditoria + índice vetorial sobrevivem a redeploy)
  • HTTPS válido na URL pública do servidor (obrigatório para Telegram/WhatsApp aceitarem o webhook)
  • Rate limit ajustado em agent.config.json conforme volume esperado
  • Alerta de handoff configurado — handoffNotifier: "webhook" + HANDOFF_WEBHOOK_URL apontando para Slack/canal do time
  • Health check (/health) integrado ao monitoramento de infraestrutura

Canais

  • Webhook do canal configurado e testado isoladamente (mensagem simples, sem LLM, se possível)
  • Número/bot de PRODUÇÃO separado do ambiente de teste
  • TELEGRAM_WEBHOOK_SECRET configurado (Telegram) — evita webhook falso

Lançamento

  • Soft-launch: só uma fração dos contatos (ex.: novos leads) passa pelo bot na primeira semana
  • Atendimento humano continua paralelo durante o soft-launch
  • Rotina semanal de auditoria de amostra agendada (Fase 7)
Não pule o soft-launch Ir direto para 100% do volume é o erro que transforma um problema de prompt em problema de reputação — um cliente que recebe resposta errada em massa não volta.

11. Segurança e segredos

  • .env nunca deve ser commitado — já está no .gitignore do projeto.
  • Use TELEGRAM_WEBHOOK_SECRET em produção — sem ele, qualquer pessoa que descubra a URL do webhook pode enviar mensagens falsas para o agente processar.
  • A verificação do webhook do WhatsApp (WHATSAPP_VERIFY_TOKEN) só protege o handshake inicial — a Meta não assina cada mensagem individualmente por padrão neste fluxo simples; trate a URL do webhook como não-pública mesmo assim.
  • Rotacione chaves de API (Anthropic/OpenAI/Voyage) periodicamente e imediatamente se algum .env vazar acidentalmente.
  • O log de auditoria (data/audit-log.jsonl) contém texto de conversas reais de clientes — trate como dado sensível (acesso restrito, backups seguros, conformidade com LGPD se aplicável).
